# CCPoC Proof-of-Capacity research and proposed protocol

## Why Burst/Signum is the closest comparison

Classic Burst/Signum plotting creates nonce data ahead of time. A nonce contains 4,096 scoops of 64 bytes each (two 32-byte hashes per scoop), for 256 KiB per nonce. A generation signature selects one scoop number from 0–4,095. A miner evaluates that same scoop position across its nonces and submits a deadline candidate. The node recomputes the deadline from the scoop data and generation signature. This means a valid design normally accepts any nonce's leaf at the selected slot; selecting exactly one absolute index for the entire plot would remove the search over nonces and would not implement Burst-style capacity weighting.

## What is inconsistent in the current CCPoC layout

CCPoC currently declares `SCOOP_SIZE = 32`, `SCOOPS_PER_NONCE = 8192` and previously used `MINING_SCOOP_MODULUS = 4096`. Because each committed leaf is a single 32-byte value, using modulus 4,096 made two leaf positions per nonce eligible. This review branch changes the modulus to 8,192: in the declared CCPoC layout, one target leaf slot now occurs per complete nonce.

This is **Burst-inspired sampling semantics, not Burst-compatible plot data**. Burst scoops are 64 bytes and the plot format/reordering algorithm matters; changing the modulus alone does not implement Shabal plot generation.

## Why Merkle inclusion does not prove disk capacity

A Merkle proof proves that a leaf belongs to a given root and position. It does not prove that the leaf was generated by a costly canonical plot algorithm, that the tree was committed before the challenge, or that the miner currently stores the rest of the plot.

In the current node:
- plot registration is performed through an API and saved in local SQLite state, rather than requiring a plot commitment transaction validated as part of canonical chain state;
- the leaf is not recomputed from a canonical plot identifier and nonce;
- a verifier can accept a winner proof when it has no local copy of that plot commitment;
- the registration API uses replacement semantics for an existing `(plot_id, miner)` row.

A commitment can therefore describe an arbitrary set of leaf values. The capacity metadata checks prevent inconsistent size/count claims, but those checks do not prove physical storage.

## Suggested v4 protocol design

1. **Freeze one data layout.** Either retain 8,192 32-byte leaves per nonce as this branch does, or adopt the Burst layout of 4,096 64-byte scoops. Do not mix scoop size, leaf size, number of entries per nonce, and the challenge modulus. Publish test vectors before implementation.
2. **Canonical plot construction.** Define the generation algorithm and all encoding, endianness, hashing, and ordering rules. The verifier must be able to establish that submitted data is valid for its plot/nonce; an arbitrary Merkle tree must not be enough.
3. **Consensus-anchored commitments.** Require the miner to commit to the root, plot identifier, owner key, format version, and capacity through a canonical transaction/state transition before the plot can be challenged. The commitment must be immutable for that plot ID. Registration age and updates must be consensus state, not local timestamps.
4. **Sample the same slot across the plot.** Derive the slot from an unpredictable challenge and iterate that slot across each nonce. For the current 32-byte format the slot range is 0–8,191. A miner may evaluate all nonces and submit the best deadline, as in Burst-style mining. The absolute index must be `nonceIndex * SCOOPS_PER_NONCE + targetSlot`.
5. **Choose realistic storage-hardness assumptions.** A simple `SHA256(plotId || index)` leaf generator is not enough: it may be cheaper to regenerate the data than to store it. Burst's iterative Shabal plotting and Chia's multi-table Proof of Space construction are relevant comparison points. Chia specifically designed its construction to make time-memory trade-offs expensive; it uses seven tables and has substantially different plotting/proving costs.
6. **Activate with a consensus fork.** The modulus change in this branch changes which proofs are valid. A real network needs a specified activation height/version, coordinated miner releases, historical replay tests, reference vectors, adversarial fake-plot/grinding tests, and independent multi-node validation.

## Scope of this branch

This branch implements the narrow sampling-parameter alignment and tests the layout arithmetic. It does **not** claim that CCPoC is now a secure Proof-of-Capacity construction. A full fix needs a plot-generation implementation and miner software that are not present in this repository, plus consensus-anchored plot registration and a coordinated protocol activation.
